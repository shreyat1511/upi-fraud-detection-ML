# Experiment design: PaySim proxy for UPI transaction fraud detection

## Study framing

The project studies transaction fraud classification using PaySim. PaySim is **synthetic mobile-money transaction data**, generated by a simulator calibrated from aggregated mobile-money activity. It is not actual UPI, NPCI, or Indian bank transaction data. Results must be described as performance on a synthetic mobile-money proxy and must not be presented as measured UPI performance.

The task is binary prediction of `isFraud` from a deliberately small, pre-transaction feature set. This design prioritizes a transparent chronological benchmark and a manageable set of interpretable baselines. No model has been trained as part of this design.

## 1. Feature and target decisions

| Role | Fields | Decision |
|---|---|---|
| Candidate predictors | `step`, `type`, `amount` | Use initially. `step` provides relative simulation time, `type` identifies transaction category, and `amount` is the transaction amount. |
| Target | `isFraud` | Binary outcome to predict. |
| Exclude: identifiers | `nameOrig`, `nameDest` | Exclude from initial model. Both are high-cardinality identifiers; `nameOrig` is nearly unique per row. They could cause memorization and entity leakage, particularly with random splitting. Do not automatically encode/use them. |
| Exclude: balances | `oldbalanceOrg`, `newbalanceOrig`, `oldbalanceDest`, `newbalanceDest` | Explicitly excluded as requested. They can reveal account state and simulator outcome mechanics; post-transaction balances are unavailable at pre-authorization time. |
| Exclude: rule flag | `isFlaggedFraud` | Exclude as a predictor because it is a related rule-generated flag and may provide a shortcut to the target. |

This feature set is an initial baseline, not a claim that all values are available at a production authorization point. PaySim's `step` and transaction fields are simulator data; explain their limitations when interpreting results.

## 2. Chronological split investigation

The CSV contains 6,362,620 records with `step` values 1–743. A pure 70/15/15 allocation by rows would cut through groups of transactions sharing a step. The candidate boundaries below keep every step intact and are close to the requested proportions. The script and reported counts use inclusive ranges.

| Split | Step range | Records | Approx. share | Legitimate | Fraud | Fraud rate |
|---|---:|---:|---:|---:|---:|---:|
| Train | 1–322 | 4,433,703 | 69.68% | 4,430,070 | 3,633 | 0.081941% |
| Validation | 323–377 | 973,173 | 15.29% | 972,603 | 570 | 0.058571% |
| Test | 378–743 | 955,744 | 15.02% | 951,734 | 4,010 | 0.419568% |
| **Total** | **1–743** | **6,362,620** | **100.00%** | **6,354,407** | **8,213** | **0.129082%** |

The boundaries are the nearest practical whole-step approximation to 70%, 85%, and 100% cumulative rows while preserving step groups: step 322 ends at about 69.68%; step 377 ends at about 84.98%. The resulting validation share is 15.29% because step 377 contains 18,183 rows. The test begins at step 378.

### Fraud-example sufficiency and distribution

All three partitions contain fraud examples: 3,633 in training, 570 in validation, and 4,010 in test. These counts support fitting and calculating validation/test metrics, although the validation set has fewer positives and should be interpreted with uncertainty intervals or caution when comparing small metric differences.

Fraud prevalence is not stable over the timeline: training has 0.081941%, validation 0.058571%, and test 0.419568%. This is a substantial temporal shift, not a reason to switch silently to a random split. Retain the chronological split as the primary realistic evaluation; report the prevalence shift and interpret performance as a later-period stress test. Before model training, inspect fraud counts by step and evaluate whether the sharp late-period increase reflects the simulator's design. Do not rebalance validation or test to force matching class rates.

The 70/15/15 split is suitable to proceed with as a **proposed chronological design**: each split has a useful number of fraud examples, all step groups remain intact, and the distribution shift is visible and measurable. Do not use a random split for the primary result.

## 3. Reproducible preprocessing

Implement preprocessing inside a scikit-learn `Pipeline`/`ColumnTransformer` fitted on the training partition only. Freeze the fitted transformations before applying them to validation and test.

1. **Input and target:** Retain only `step`, `type`, `amount`, and `isFraud`. Assert expected columns, nonmissing values, and binary target. Keep the raw CSV unchanged.
2. **Categorical `type`:** One-hot encode with `handle_unknown="ignore"`. Fit category vocabulary on training data only. Do not ordinal-encode transaction types as if their codes had numeric order.
3. **Numerical `amount`:** It is nonnegative and highly right-skewed. Apply `log1p` then `StandardScaler` for Logistic Regression; learn scaler parameters on training only. Tree models do not require scaling; use the same log-transformed amount representation for a consistent, stable comparison or document a per-model transform choice.
4. **Numerical `step`:** Treat as numeric relative time. Standardize for Logistic Regression using training-only statistics. Tree models can use raw step values. Do not infer calendar date or seasonality from it.
5. **Class imbalance:** Keep validation and test at their natural observed prevalence. Start with `class_weight="balanced"` for Logistic Regression and Decision Tree; for Random Forest use `class_weight="balanced_subsample"` (or balanced weights). Weights are computed during training; do not duplicate, oversample, or undersample validation/test. If resampling is later explored, place it inside an imbalanced-learn training pipeline so it runs only on each training fold.
6. **Reproducibility:** Record library versions, random seeds for models, exact input filename/checksum, split boundaries, feature list, preprocessing parameters, and model configuration. This design does not currently produce model results.

Suggested transformation layout:

| Model family | `type` | `amount` | `step` | Imbalance handling |
|---|---|---|---|---|
| Logistic Regression | One-hot | `log1p` then train-fit standard scaling | Train-fit standard scaling | Balanced class weights |
| Decision Tree | One-hot | `log1p` (no scaling needed) | Raw numeric | Balanced class weights |
| Random Forest | One-hot | `log1p` (no scaling needed) | Raw numeric | Balanced subsample weights |

## 4. Manageable model comparison

- **Logistic Regression:** Regularized linear baseline; quick to fit and helps establish whether a simple additive boundary carries useful signal. Class weights address unequal error costs and prevalence during fitting.
- **Decision Tree:** Nonlinear, human-readable baseline that can expose simple interactions among amount, transaction type, and step. Control depth/minimum leaf size using validation data to reduce overfitting.
- **Random Forest:** Ensemble of trees that captures nonlinearities and interactions more robustly than one tree. It provides a stronger tabular baseline at higher compute cost and is less directly interpretable.

Use fixed training/validation/test partitions for all three. Tune only a small, predeclared set of hyperparameters using the training/validation data; reserve the test partition for the final comparison after choices are frozen. Do not repeatedly select models based on test performance.

## 5. Evaluation metrics and decision procedure

Report the positive-class confusion matrix in the conventional order `[[TN, FP], [FN, TP]]`, with exact counts. Include:

- **Precision:** Of transactions flagged as fraud, the fraction labeled fraud; reflects false-alarm burden.
- **Recall:** Of labeled fraud transactions, the fraction detected; reflects missed-fraud burden.
- **F1-score:** Harmonic mean of precision and recall; summarize the chosen threshold, not the entire ranking.
- **PR-AUC / Average Precision:** Primary threshold-independent metric for the rare positive class. State the exact implementation and whether “PR-AUC” means trapezoidal area or Average Precision.
- **Confusion matrix:** Essential at the selected operating threshold; report FP and FN alongside rates and class counts.
- **Additional context:** Fraud prevalence and threshold-specific precision/recall. ROC-AUC can be included secondarily but should not replace precision-recall measures under severe imbalance.

Choose a threshold on validation data based on the project’s explicit operating objective (for example, a minimum recall or an acceptable false-positive volume). Freeze it, then evaluate once on test. Do not claim a universal “best threshold” without an operational cost assumption. The late test period’s higher fraud prevalence can materially affect precision; report that prevalence beside all test metrics.

## 6. Risks and interpretation limits

- PaySim is synthetic mobile-money data, not UPI; this benchmark cannot establish effectiveness on actual UPI traffic.
- Simulator patterns and labels may be easier or different from real-world fraud. Avoid generalizing the model beyond the dataset.
- The strong fraud-prevalence shift across the chronological partitions may affect precision and calibration. This is a finding to report and analyze, not to conceal through resampling or random splitting.
- The selected features intentionally exclude entity IDs and balances, limiting both leakage risk and potentially useful historical behavior. Any later feature expansion requires a feature-availability and temporal-leakage review.
- `step` has no calendar meaning. The split evaluates ordered simulator time, not seasonal behavior or long-term deployment drift.

## 7. Preparation script

[`scripts/prepare_dataset.py`](../scripts/prepare_dataset.py) reproduces the split counts using the boundaries in this document. By default it reads the raw CSV and prints counts only. It can optionally write feature/target-only partition files (without altering the raw CSV):

```powershell
python scripts/prepare_dataset.py
python scripts/prepare_dataset.py --write-splits
```

The optional files go to `data/processed/`. The script does not fit preprocessing transforms or train models. Model training requires a separate approval.
